# フラクタル映像制作ハーネス 仕様書

状態: ドラフト v0.1（2026-11-15）／対象ブランチ: `harness-with-fable5.2`（`main` 起点）

本書は、LLMエージェントが複数カットのフラクタル映像を自律的に設計・レンダリング・動画化するためのハーネスの仕様を定める。旧 `harness` ブランチの実装は引き継がず、`main` の `renderer-core` / `renderer-cli` の上に新規に構築する。

数値の閾値と既定値はすべて**暫定**であり、調整用設定（3.3）に切り出してある。全工程の実装後に、13章の較正手順でまとめて調整する。

---

## 1. 目的と非目的

### 目的

- エージェントが人手の介入なしに、企画から YouTube へアップロード可能な MP4 までを完成させる。
- 作品ごとに**構造的に異なる**映像が出る（既存作品の変種にならない）。
- 完成尺あたりの GPU 時間に上限があり、**見やすい**画が出る。
- 本番レンダリングは GPU を占有しきらない設定で実行でき、中断から再開できる。

### 非目的

- 音声、字幕、タイトル、サムネイルの生成。
- YouTube へのアップロード自体。
- 任意の WGSL の受け入れ（型付き DSL の範囲に留める）。
- 複数 GPU・複数マシンでの分散レンダリング。

## 2. 設計原則

旧ハーネスで出た2つの問題と、それに対する原則の対応を示す。

| 問題 | 旧ハーネスでの原因 | 原則 |
|---|---|---|
| 既存作品の変種になる | 入口が既存シーンの取り込みと `scene.patch` で、探索空間が既存シーンの近傍に固定されていた | P1 企画層の分離、P2 探索による形状発見、P7 情報隔離 |
| 重いわりにごちゃごちゃする | 品質設定をエージェントが自由に決め、コストは設計後に測るだけだった。評価指標が contrast と edge density だった | P3 品質設定のハーネス所有、P4 読みやすさ指標、P5 批評の分離 |

- **P1 企画層の分離**: 設計は「ブリーフ → カット割り → ルック」の順に行い、多様性は企画層のカテゴリ軸で判定する。
- **P2 探索による形状発見**: 形状の数値はエージェントが書かない。ハーネスが広くサンプリングし、エージェントは画像を見て選ぶ。
- **P3 品質設定のハーネス所有**: `render` と `quality` はハーネスが決める。エージェントは効果を「要求」でき、ハーネスが有無比較で採否を決める。
- **P4 読みやすさ指標**: 細部の多さは加点しない。縮小時と圧縮後に読めることを合格条件にする。
- **P5 批評の分離**: 設計役と批評役は別コンテキストにする。批評役は画像・動画とブリーフだけを見る。
- **P6 コードによる工程強制**: 工程の順序とゲート判定はハーネスのコードが行う。プロンプトでの依頼に頼らない。
- **P7 情報隔離**: 設計役は過去作のシーン定義を読めない。過去作については台帳の軸値だけを知る。
- **P8 本番は決定的ジョブ**: 本番レンダリング中に LLM の判断を挟まない。エージェントは起動と監視だけを行う。

## 3. 全体構成

```text
┌──────────────── エージェント層（Claude Code）────────────────┐
│  監督 (director)        … 工程を進める主エージェント          │
│  批評 (critic)          … 別コンテキストのサブエージェント     │
└───────────────┬──────────────────────────────────────────────┘
                │ CLI 呼び出し（stdout は JSON 1個）
┌───────────────▼──────────────────────────────────────────────┐
│  fractal-harness（新規 crate: renderer-harness）              │
│   工程状態機械 / 台帳 / ロケハン / 指標 / 予算 / ジョブ管理    │
└───────────────┬──────────────────────────────────────────────┘
                │ ライブラリ呼び出し
┌───────────────▼──────────────────────────────────────────────┐
│  renderer-core（既存）        FFmpeg / ffprobe（外部）         │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 コンポーネント

| 名前 | 形態 | 役割 |
|---|---|---|
| `fractal-harness` | Rust CLI（`renderer-harness` crate） | 工程管理、ゲート判定、ロケハン、指標計算、品質決定、本番ジョブ、エンコード、QC |
| 監督スキル | `.claude/skills/fractal-film/SKILL.md` | 監督エージェントの手順。`fractal-harness next` の指示に従うことだけを定める |
| 批評エージェント | `.claude/agents/film-critic.md` | ルーブリックに沿った判定を JSON で返す |
| 台帳 | `portfolio/ledger.jsonl`（git 管理） | 完成作品の軸値、画像記述子、実績コスト |
| 制作ディレクトリ | `output/productions/<id>/`（git 管理外） | 1作品の全状態と成果物 |

`fractal-harness` は常駐サーバーにしない。各コマンドは1回で終了し、状態はすべて制作ディレクトリに置く。旧ハーネスの JSONL サーバーと冪等性キーは採用しない。

### 3.2 制作ディレクトリ

```text
output/productions/<id>/
├── state.json              # 現在の工程、ゲート結果、反復回数、破棄回数
├── mandate.json            # ハーネスが引いた制約（6.2）
├── budget.json             # 予算と消費実績
├── scout/                  # ロケハン候補、コンタクトシート、選択結果
├── brief.yaml              # 監督が書く
├── shotlist.yaml           # 監督が書く
├── look.yaml               # 監督が書く
├── compiled/cut-NN.yaml    # ハーネスが生成する実シーン（監督は編集不可）
├── animatic/               # 低解像度の全尺動画と指標
├── proof/                  # 本番品質の抜粋、有無比較、時間実測
├── reviews/                # 批評役の判定 JSON
├── frames/cut-NN/          # 本番 PNG 連番
├── jobs/                   # ジョブのマニフェストとログ
└── final/<id>.mp4          # 完成動画、QC 結果
```

### 3.3 調整用設定（Tuning）

閾値、上限、参照する作品数、構図の距離など、方針に属する固定値はすべて1つの設定にまとめる。コードに直接書くのは、光線の本数や文字の大きさのような仕組み側の値だけとする。

| グループ | 内容 |
|---|---|
| `diversity` | 形状族の禁止に使う作品数、軸差分の比較対象数と必要な差分数、指定する軸の数、新規性ゲートの距離 |
| `limits` | 工程ごとの `revise` 回数、`kill` 回数、指定制約の引き直し回数 |
| `scouting` | 1ラウンドの形状数、選べるロケ地数、俯瞰のカメラ距離、中景・近景の余裕の範囲、被写体距離、画角、フォグ、コスト見積もりの spp と上限比、近傍探索の幅 |
| `legibility` | 余白率の下限と上限、高周波比の上限、最低輝度、フリッカーの上限 |
| `classification` | 距離域・光・テンポ・パレットの分類境界 |
| `shotlist` | トランジションの長さ、カット尺の範囲、連続カットに必要な差分数、経路の余裕の下限 |
| `quality` | 基準 spp、有無比較の spp、spp と epsilon の段、各知覚差の閾値 |

- 設定は YAML ファイルで与える。書かれていない項目は既定値のままになる。知らない項目名は誤記として拒否する。
- `init` は `--tuning <file>` で指定されたファイル、なければ作業ディレクトリの `harness-tuning.yaml`、それもなければ既定値を使う。
- 制作は作成時の設定を `tuning.json` として保持し、以後はそれだけを使う。設定ファイルを後から変えても、進行中の制作のルールは変わらない。
- `tuning show` は現在の設定を表示し、`tuning write <path>` は編集用の YAML を書き出す。リポジトリには既定値を書き出した `harness-tuning.yaml` を置いてある。

これとは別に、作品ごとの構図は監督が `shotlist.yaml` で決める（5.2 の `distance`）。

### 3.4 エージェントが書けるもの

監督が直接書けるのは `brief.yaml`、`shotlist.yaml`、`look.yaml` の3つだけとする。`compiled/` はハーネスが3ファイルとロケ地と品質決定から生成する。監督が `compiled/` を書き換えた場合、ハーネスは内容ハッシュの不一致で以降のコマンドを拒否する。

## 4. 工程

工程は一方向の状態機械で、各工程の出口にゲートがある。ゲートの判定はハーネスが行い、通過しない限り次工程のコマンドは拒否される。工程の全ゲートが合格した時点で、判定したコマンドがそのまま次工程へ進める。「進む」ための独立したコマンドはない。ゲートの結果は工程を離れるときに履歴へ残す。

```text
S0 開始 → S1 ロケハン → S2 ブリーフ → S3 カット割り → S4 ルック
       → S5 プルーフと予算 → S6 本番 → S7 エンコードと QC → 完了
                ▲                                  
                └──── 破棄（S2〜S5 から S1 へ戻る）
```

| 工程 | 監督の作業 | ハーネスの成果物 | ゲート |
|---|---|---|---|
| S0 開始 | `init` を実行 | `mandate.json`、`budget.json` | なし |
| S1 ロケハン | コンタクトシートを見てロケ地を選ぶ | 候補サムネイル、候補ごとの指標とコスト | 選んだ全ロケ地が新規性ゲート（6.4）とコスト上限（8.2）を通過 |
| S2 ブリーフ | `brief.yaml` を書く | 軸値の検証結果 | スキーマ、指定制約の充足、軸差分ルール（6.3） |
| S3 カット割り | `shotlist.yaml` を書く | 経路検査、アニマティック動画、指標 | 経路の安全性、作品内の重複禁止（7.2）、読みやすさ指標（9章）、批評の合格 |
| S4 ルック | `look.yaml` を書く | ルック確認用プレビュー | 色相数、白飛び・黒潰れ、批評の合格 |
| S5 プルーフと予算 | 効果を要求する。超過時は尺や内容を見直す | 効果の有無比較、品質決定、時間見積もり、プルーフ動画 | 予算（8.1）、圧縮耐性、フリッカー、批評の最終合格 |
| S6 本番 | `produce` を起動し監視する | PNG 連番 | 全フレームの存在とデコード検証 |
| S7 エンコードと QC | `encode` を実行 | MP4、QC 結果、台帳への追記 | 12.2 の QC 全項目 |

### 4.1 反復と破棄

- 批評の判定は `pass`、`revise`、`kill` の3種類とする。
- `revise` は1工程あたり最大3回。超えた場合、最も評価の高かった版で先へ進み、台帳に `compromised: true` を記録する。
- `kill` は S1 へ戻る。使っていたロケ地はその制作内で再選択できない。1制作あたり最大2回。批評役の `kill` が上限を超えた場合は `revise` 上限と同じ扱いにする。監督自身による `kill` は上限を超えると拒否する。
- 批評役の判定は、その工程の測定系ゲートがすべて合格した後にだけ登録できる。`revise` を受けると測定系ゲートも未判定へ戻り、作り直した成果物で測り直す。
- S6 に入った後は設計へ戻らない。

### 4.2 `next` コマンド

監督は工程を覚える必要がない。`fractal-harness next <id>` が、現在の工程、未達のゲート条件、次に実行できるコマンド、読むべき成果物のパスを返す。監督スキルは「`next` を呼び、指示に従い、完了まで繰り返す」ことだけを定める。

## 5. データスキーマ

### 5.1 `brief.yaml`

```yaml
version: 1
title: "…"
subject: "一文で言える主題"        # 批評役が画像と照合する。1行、120字以内
axes:
  scale_regime: mid                 # overview | mid | deep
  motion: flyover                   # dive | orbit | multi-dive | flyover
  palette: { primary_hue: amber, key: high }
  light: backlit                    # frontal | raking | top | backlit
  pacing: medium                    # slow | medium | fast
locations: [loc-0142, loc-0377]     # S1 で選んだ ID。先頭が主ロケ地
arc: "導入で全体像、中盤で内部、終盤で引いて終わる"
```

`formula_family` は書かない。主ロケ地（`locations` の先頭）の形状族がそのまま作品の値になる。

ブリーフの `axes` は宣言であり、S2 では宣言値に対して指定制約と軸差分ルールを判定する。確定した6軸は `axes.json`（ハーネス所有）に保存し、S3 と S4 で成果物から算出した値がこれと一致することを検証する。一致しなければ、その工程のゲートを不合格にする。

### 5.2 `shotlist.yaml`

```yaml
version: 1
format: { width: 1920, height: 1080, fps: 30 }
cuts:
  - id: 1                     # 1 からの連番
    role: establishing        # establishing | dive | detail | reveal | transit
    location: loc-0142        # ブリーフに書いたロケ地
    viewpoint: vp-1           # ロケハンで選別を通った視点
    motion: { kind: orbit, revolutions: 0.15 }
    duration_seconds: 8.0
    transition_out: crossfade # cut | fade-black | crossfade。最終カットは cut
```

監督はカメラ座標を書かない。`location` と `viewpoint` の ID、および相対的な運動指定だけを書き、ハーネスが絶対座標と経路パラメータへ変換する。

| `motion.kind` | 指定 | 内容 |
|---|---|---|
| `orbit` | `revolutions`（符号つき、絶対値0.01〜1）、`distance`（省略時1） | 視点の位置から、視点の被写体を中心に周回する |
| `dive` | `depth`（終了距離/開始距離、0.001〜0.9）、`hold_seconds`（省略時0）、`distance`（省略時1） | 視点の位置から、視線に沿って被写体へ寄る |
| `flyover` | `travel`、`height`（いずれも形状の半径比）、`look_ahead` | ハーネスが探した表面の上を滑空する。視点は光源だけを与える。有界な形状のみ |
| `multi-dive` | `depth`、`dives`（1〜4） | ハーネスが探した複数の特徴へ、暗転を挟んで順に寄る。有界な形状のみ |

`distance` は開始時のカメラ距離を、ロケハンの視点の距離に対する倍率（0.2〜4）で指定する。1未満で被写体が大きく写る。視線の向きは変わらない。寄せすぎて表面に近づいた場合は経路検査が落とす。

`format` は 1280×720、1920×1080、2560×1440、3840×2160 と 24・25・30・48・50・60fps に限る。フェードとクロスフェードは0.5秒で、前後のカットは2秒以上必要。クロスフェードは2カットを重ねるので、作品の尺はその分だけ短くなる。

`shotlist check` は各カットを `compiled/cut-NN.yaml` へコンパイルし、内容ハッシュつきの `compiled/manifest.json` を書く。後続のコマンドは、`shotlist.yaml` がチェック後に変更されていれば拒否する。

### 5.3 `look.yaml`

```yaml
version: 1
material: { ... }             # DslMaterial の項目
light: { direction: [...] }
tone_mapping: { ... }
post_process: { ... }
per_cut: { 3: { light: { direction: [...] } } }   # カット別の上書き
effects_requested:            # 既定はすべて off
  ambient_occlusion: true
  soft_shadow: false
  reflection: false
  depth_of_field: false
```

`render` と `quality` の数値（解像度、spp、各ステップ数、epsilon）は書けない。書かれていたらスキーマ検証で拒否する。

### 5.4 台帳 `portfolio/ledger.jsonl`

1行1作品。完成時にハーネスが追記する。

```json
{"id":"…","date":"2026-11-15","title":"…","axes":{…},
 "descriptors":[{"structure":[…],"colour":[…]}],
 "keyframes":["portfolio/keyframes/<id>/frame-000000.png"],
 "duration_seconds":62.0,"gpu_minutes":118.4,"compromised":false}
```

`descriptors` はキーフレーム1枚につき1個。`gpu_minutes` は後から取り込んだ作品では不明のため省略できる。

ハーネス以前の作品は `ledger import <scene.yaml> --id … --title … --date …` で登録する。シーンから形状族と運動、中間フレームのカメラから距離域と光、始点・中間・終点の縮小描画からパレットと記述子を算出する。既存の7作品は登録済みで、結果は次のとおり。

| 作品 | 形状族 | 距離域 | 運動 | 主色相 | 光 | テンポ |
|---|---|---|---|---|---|---|
| mandelbox-quad-zoom | mandelbox | deep | dive | amber | frontal | slow |
| mandelbox-first-descent | mandelbox | deep | dive | amber | raking | slow |
| midnight-opal | mandelbox | deep | multi-dive | teal | frontal | slow |
| verdigris-atlas | mandelbox | mid | flyover | green | raking | slow |
| alchemy-orbit | amazing-hybrid | deep | orbit | amber | frontal | slow |
| ivory-vault | amazing-hybrid | deep | orbit | neutral | frontal | slow |
| azure-cloister | amazing-hybrid | deep | orbit | teal | frontal | medium |

旧ハーネスで作った後ろの3作品は、主色相（とテンポ1件）以外の全軸が同じである。ivory-vault と azure-cloister のシーンは、このブランチにない経路パラメータ（`end_radius`、`smooth_start_stop`）を外して取り込んだため、キーフレームの構図は実際の作品とわずかに異なる。

## 6. 多様性の仕組み

### 6.1 軸

| 軸 | 値の例 | 決まり方 |
|---|---|---|
| `formula_family` | `mandelbulb`、`mandelbox`、`rotated-mandelbox`、`julia-box`、`amazing-surf`、`mandelbox-julia`、`amazing-hybrid` | orbit 命令の集合から自動分類 |
| `scale_regime` | `overview`、`mid`、`deep` | カメラ距離と形状の外接半径の比から自動分類 |
| `motion` | `dive`、`orbit`、`multi-dive`、`flyover` | 尺が最長の経路種別 |
| `palette` | 主色相 `red`、`amber`、`green`、`teal`、`blue`、`violet`、`neutral` | `look.yaml` から自動抽出。明度キー（`low`、`mid`、`high`）も記録するが、軸の比較は主色相だけで行う |
| `light` | `frontal`、`raking`、`top`、`backlit` | 光の向きと視線の関係から自動分類。レンダラーの光源は向きだけを持つため、色温度は `palette` 側で扱う |
| `pacing` | `slow`、`medium`、`fast` | 平均カット尺から自動分類 |

軸値は監督の自己申告ではなく、成果物からハーネスが算出する。

### 6.2 指定制約（mandate）

`init` 時にハーネスが乱数で次を引き、`mandate.json` に書く。乱数は LLM ではなくハーネスが生成する。

- **禁止**: 直近3作品で使われた `formula_family`。ロケハンのサンプリングからも除外する。
- **指定**: 6軸のうち2軸について、台帳で使用回数が最も少ない値の中から1つずつ。

抽選時点で両立しないと分かっている組み合わせは引かない。現在の登録は「`flyover` と `overview`」の1組（滑空は表面から半径の数割の高さを保つため、形状全体が見える距離にならない）。

指定が実現不能な場合は、ハーネスがその軸を引き直す。ハーネスが検出するのは次の2つである。

- **運動**: `brief check` の時点で、指定された運動（`flyover` と `multi-dive`）の標準的な経路を、選択済みのどのロケ地でも計画できない。
- **形状族**: `scout run` の1ラウンドで、指定された形状族から選別を通る候補が1つも出ない。

それ以外の軸や、軸どうしの組み合わせによる実現不能は検出しない。行き詰まった場合は監督が `kill` する。

実現できない組み合わせが存在すること自体は、探索空間が広いことの表れであり、問題として扱わない（2026-11-15 決定）。修正対象とするのは、それによって計算時間が極端に伸びる場合と、回帰評価（13.2）の完走率が50%を下回る場合である。

- 引き直しはハーネスが実現不能を検出したときだけ行う。監督が任意に引き直すコマンドはない。
- 引き直すのは実現不能だった軸だけで、同じ軸の、まだ試していない値のうち使用回数が最も少ないものから選ぶ。
- 1制作あたり2回まで。使い切った後も実現不能なら没案とし、`kill` と同じく S1 へ戻る（使ったロケ地は再選択不可、`kill` の回数を1回消費）。
- `kill` の回数も使い切っている場合は、その軸の指定を外して続行し、台帳に `compromised: true` を記録する（4.1 の上限到達時の扱いに合わせた）。

### 6.3 軸差分ルール

新作は、台帳の直近5作品のそれぞれに対して、6軸中3軸以上が異なること。満たさない場合、S2 のゲートで却下する。

### 6.4 画像新規性ゲート

`scout select` で、選んだロケ地の選別済みサムネイルと台帳の全キーフレームについて構造記述子の距離を計算し、最小値が閾値（暫定0.10）未満なら不合格とする。台帳にキーフレームがなければ合格とする。

- 構造記述子: 輝度分散のスケール別の割合（5値）、エッジ方向のヒストグラム（8値）、6×6 の明暗配置（36値）。色に依存しないので、灰色のロケハン画像と着色済みのキーフレームを比較できる。距離は3成分の平均で0〜1。
- 色記述子: 色相ヒストグラムと平均彩度・平均輝度。台帳に記録するが、S1 の判定には使わない。
- Rust で実装し、外部モデルに依存しない。

**実測で分かった限界**: この記述子が測るのは「画像として似ているか」であり、「同じ形状か」ではない。ロケハン画像162枚では、同じ形状の別視点どうしの距離（中央値0.30）と別形状どうしの距離（中央値0.31）に差が出なかった。既存作品では、同じ形状を使う ivory-vault と azure-cloister が0.126、無関係な作品どうしが0.165〜0.263で、閾値0.10ではこの組を検出できない。一方、閾値を上げるとロケハン画像の誤検出が増える（別形状の組の1%が0.12未満）。したがって現状のゲートは、ほぼ同じ構図の再利用だけを止める弱い足切りである。形状レベルの重複は、形状族の禁止、軸差分ルール、台帳のキーフレームを見る批評役が担う。学習済み画像埋め込みは導入しない（2026-11-15 決定）。

### 6.5 情報隔離

- 監督と批評役に対し、`scenes/examples/**`、`scenes/production/**`、他の制作ディレクトリ、`output/` 直下の旧成果物の読み取りを `.claude/settings.json` の deny ルールで禁止する。
- シーンの語彙は `fractal-harness describe` が返すスキーマと命令一覧だけから得る。
- 過去作について監督に渡すのは、台帳の軸値の一覧だけとする。批評役には過去作のキーフレーム画像も渡す（変種かどうかの判定用）。

## 7. ロケハンとカット割り

### 7.1 ロケハン（S1）

1. **形状の生成**: 指定制約で許された族を順に回し、族ごとのテンプレートから orbit プログラムと係数を乱数生成する。反復数は10〜24とし、形状の一部としてこの段階で固定する。
2. **CPU での足切り**: 半径24から原点へ向けて96本の光線を CPU の距離推定で飛ばす。距離推定が非有限になるもの、命中が2割未満のもの、小さすぎるものを捨てる。命中半径の9割点が10以上の形状は「非有界」（空間を埋める形状）として扱う。
3. **視点の探索**: 有界な形状は俯瞰・中景・近景、非有界な形状は中景2つと近景を探す。俯瞰は外接半径の2.6倍の距離から原点を見る。中景と近景は、表面までの距離がスケール域ごとの範囲に入る空間内の点を探し、24方向のうち「被写体までの距離が適切」かつ「周囲5本の光線の奥行きがばらつく」向きを選ぶ。
4. **サムネイル描画**: 320×180・1spp・二次効果なし・中立の灰色マテリアルで描画する。奥行きを分けるフォグは被写体距離に合わせて視点ごとに設定する。GPU デバイスはラウンド全体で1つを使い回し、シェーダーだけを差し替える。組み込みの Mandelbulb は専用マテリアルを持たないため、既定の配色で描画される。
5. **選別**: 読みやすさ指標（9章）と推定コストで足切りする。除外理由は `cost`（推定が `max_frame_seconds` の半分を超える）、`dark`、`empty`（余白率が85%超）、`cluttered`（余白率が10%未満、または高周波エネルギー比が0.35超）。推定コストは、サムネイルの GPU 時間を 1920×1080・8spp に画素数比で換算した値とする。
6. **コンタクトシート**: 選別を通った視点だけを、6×4 の一覧画像に「ロケ地番号-視点番号」のラベル付きで並べる。個別のサムネイルも保存する。
7. **選択**: 監督が画像を見て `scout select` でロケ地を2〜5個選ぶ。`scout run --around <loc>` は、その形状の全係数を±12%の範囲で動かした近傍を探す。

1回の `scout run` の既定は60形状とする。RTX 3070・デューティ比80%での実測は、実時間約74秒、GPU 約33秒、候補約100件だった。形状の定義は `compiled/locations/<loc>/<vp>.yaml` に置き、監督が読む `scout/` には画像と指標だけを置く。

### 7.2 カット割り（S3）

- 既定の構成はカット4〜8個、総尺45〜90秒。`init --film-seconds` と `--film-cuts` で制作ごとに変えられる。
- **ブリーフとの一致**（`schema` ゲートに含む）: 尺が最長の運動、尺が最長の距離域、平均カット尺から求めたテンポが `axes.json` と一致すること。主ロケ地の画面時間が最長であること。
- **作品内の重複禁止**（`in-film-variety`）: 連続する2カットは、`role`、距離域、運動のうち2つ以上が異なること。
- **経路検査**（`route-safety`）: 各カットの全フレーム（400点を超える場合は等間隔）で、カメラ位置の距離推定を CPU で求め、被写体距離に対する比が0.02以上であること。GPU は使わない。
- **アニマティック**（`legibility`）: 全カットを 320×180・1spp・全フレームで描画し、トランジション込みで1本の MP4 にする。カットごとに読みやすさ指標（毎秒2枚の平均）とフリッカーを測る。各カットの始点・中間・終点を並べたシートも出力する。S3 の主な評価対象はこの動画とする。
- **批評**（`critic`）: `review submit --verdict pass|revise|kill --notes …` で登録する。判定は `reviews/` に残る。

距離域の分類は、カメラの余裕（距離推定）が作業半径の5%未満なら `deep`、有界な形状でカメラが中心から半径の1.5倍以上離れていれば `overview`、それ以外は `mid` とする。俯瞰を距離推定で判定しないのは、距離推定が下限値であり、表面までの距離を過小に見積もるため。

実測（5カット・47秒、RTX 3070、デューティ比80%）: アニマティック1回が実時間約27秒、GPU 約15秒。ロケハンから S3 通過までの設計工程全体で GPU 約77秒（設計予算1410秒の約5%）。

## 8. 予算と品質

### 8.1 予算

`budget.json` の既定値（暫定）:

| 項目 | 既定 | 意味 |
|---|---:|---|
| `gpu_minutes_per_output_second` | 2.0 | 本番の GPU 稼働時間の上限。1080p30 なら平均 4 秒/枚に相当 |
| `design_budget_ratio` | 0.25 | 設計工程（S1〜S5）が使える GPU 時間。本番予算に対する比 |
| `max_frame_seconds` | 12.0 | 1枚あたりの最大描画時間 |
| `max_gpu_duty_cycle` | 80 | 本番と設計の両方に適用する上限 |

予算は GPU の稼働時間で数える。デューティ比による休止時間は含めない。実時間の見積もりは別に表示する。

参考: 旧 Azure Cloister は約 10 GPU分/完成秒だった。既定値はその約1/5にあたる。

### 8.2 コスト上限と見積もり

- ロケハン時: サムネイルの実測から本番解像度・標準品質へ換算した推定値が `max_frame_seconds` の半分を超える候補は載せない。
- S5: 各カットの5地点を、本番設定の `--region` 相当（中央25%の領域）で実測し、領域比で換算して全尺を見積もる。見積もりが予算を超えたら S6 へ進めない。

### 8.3 品質決定

`render` と `quality` は S5 でハーネスが次の順に決める。

測定は各カットの3フレーム（始点、中間、終点）について、本番解像度のまま中央の領域（縦横50%、面積25%）だけを描画して行う。知覚差は `(1 − SSIM) + 平均RGB差` とし、縦横1/2に縮小した画像で、3フレーム中の最大値を採る。

1. **効果の有無比較**: 16spp で、要求された効果を1つずつ外して描画し、外す前との知覚差を測る。差が閾値未満の効果は不採用とする。採用する効果は、ステップ数を要求値の1/4、1/2の順に試し、差が閾値未満に収まる最小の段を採る。比較する2枚は同じ spp なので、サンプリングノイズは相殺される。
2. **spp の決定**: 採用した効果で 64spp の基準画像を描画する。4、8、16、32 の順に試し、基準との差が閾値未満になる最小値を採る。どれも満たさなければ 32 とする。
3. **epsilon の決定**: `pixel_epsilon_multiplier` を1.5倍、2倍、3倍の順に上げ、差が閾値を超える直前の値を採る。画素以下の細部を解像させないための設定で、速度と見やすさの両方に効く。
4. **時間見積もり**: 決定した設定での領域の GPU 時間を面積比で全画面へ換算し、3フレームの平均と最大を出す。中央は被写体があり重い領域なので、見積もりは悲観側に寄る。
5. **予算との照合**: 超過する場合、「効果を1つ落とす」と「spp を半分にする（下限2）」のうち知覚差が最も小さいものを1つずつ適用する。効果の知覚差は有無比較の値、spp の知覚差は手順2で測った基準との差を使う。手順2で試していない spp は最後に回す。それでも超過する場合は、超過量を監督に返し、尺の短縮かカットの差し替えを求める。

決定の経過は `proof/quality-decision.json` に残す。

## 9. 読みやすさ指標

すべて 320px へ縮小した画像で計算する。細部の量を加点に使う指標は置かない。

| 指標 | 定義 | 合格条件（暫定） |
|---|---|---|
| 高周波エネルギー比 | 輝度の分散のうち、4画素より細かい成分が占める割合。4倍に縮小して戻した画像との残差で測る | 上限あり |
| 余白率 | 8×8 画素のブロックのうち、輝度の標準偏差が閾値未満のものの割合 | 15〜70% |
| 色相数 | 彩度のある画素の色相を12分割し、画素の10%以上を占める区間の連なりを数えたもの | 3以下 |
| 白飛び・黒潰れ率 | 上下端に張り付いた画素の割合 | 各2%以下 |
| フリッカー | 各フレームと、その前後のフレームの平均との差の絶対値を、縦横1/2に縮小した輝度で平均したもの。滑らかなカメラ運動ではほぼ0になり、細部のちらつきで大きくなる | 0.02以下 |
| 圧縮耐性 | プルーフ動画を 1080p30・8 Mbps の H.264 で再エンコードしたときの元との SSIM | 下限あり |

圧縮耐性は S5 のみで測る。それ以外は S1（静止画のみ）、S3、S4、S5 で測る。

## 10. 批評役

### 10.1 入力

- `brief.yaml` の `title`、`subject`、`arc`
- その工程の画像・動画（S3 はアニマティックとカットごとの代表フレーム、S4 はルック確認画像、S5 はプルーフ動画と圧縮後の動画）
- 台帳のキーフレーム画像
- 指標の値と合否

`shotlist.yaml`、`look.yaml`、`compiled/`、監督の説明文は渡さない。

### 10.2 ルーブリック

各項目を合否で判定し、不合格には画像上の根拠を1文で付ける。

1. 主題が一目で分かり、`subject` と一致するか。
2. 320px の縮小画像でも主題と背景が区別できるか。
3. 台帳のどの作品とも「色違い・角度違い」に見えないか。
4. カット同士が、スケール、運動、構図のいずれかで明確に違うか（S3 以降）。
5. 動きの速さがカット尺に対して適切か。速すぎて読めない、遅すぎて止まって見える箇所はないか（S3 以降）。
6. 圧縮後に細部が潰れてノイズになっていないか（S5）。

### 10.3 出力

```json
{"verdict":"revise","failed":[2,5],
 "notes":[{"item":2,"cut":3,"reason":"…"},{"item":5,"cut":1,"reason":"…"}]}
```

項目3の不合格は `kill` とする。それ以外の不合格は `revise` とする。判定は `reviews/` に保存し、ハーネスがゲートの入力として読む。

## 11. 本番レンダリング（S6）

### 11.1 ジョブ

- `produce` はカット単位のジョブを順に実行する。1カットは `compiled/cut-NN.yaml` 1個に対応する。
- 出力は `frames/cut-NN/frame_%06d.png`。既存の検証付き resume をそのまま使う。
- マニフェストに、シーンのハッシュ、バイナリのバージョン、GPU アダプター、デューティ比、進捗、各フレームの描画時間を記録する。ハッシュが異なるフレームとは混在させない。
- 同一マシンで GPU ジョブは同時に1つだけとする。ロックファイルで排他する。
- `produce` はバックグラウンドで起動でき、`status` で進捗と残り時間の見積もりを返す。同じコマンドの再実行で再開する。

### 11.2 GPU の占有制御

- `--gpu-duty-cycle` を全 GPU コマンドに渡す。`budget.json` の `max_gpu_duty_cycle` を超える値は拒否する。
- ロケハン、アニマティック、プルーフにも同じ上限を適用する。

### 11.3 高速化の要件

- 合格条件は 8.1 の予算で定義する。「十分に高速」とは、見積もりと実績が予算内に収まることを指す。
- 実績が見積もりの1.5倍を超えたカットは、マニフェストに警告として記録する。本番中に品質を自動で変えることはしない。
- レンダラー側の高速化候補は 14.2 に挙げる。採否は実測で決める。

## 12. エンコードと QC（S7）

### 12.1 出力形式

YouTube の SDR アップロード推奨に合わせる。

| 項目 | 値 |
|---|---|
| コンテナ | MP4、moov を先頭に配置（faststart） |
| 映像 | H.264 High、プログレッシブ、yuv420p、CABAC |
| GOP | フレームレートの半分の closed GOP、連続 B フレーム2 |
| 色 | sRGB から BT.709 へ明示的に変換し、BT.709 limited range のタグを付ける |
| 品質 | CRF 16、preset slow（アップロード用の高品質原版） |
| 解像度とフレームレート | 既定 1920×1080・30fps。`shotlist.yaml` の `format` で 2560×1440、60fps を選べる |
| 音声 | なし |

トランジション（`cut`、`fade-black`、`crossfade`）は FFmpeg のフィルタで合成する。PNG 原版は保持する。

### 12.2 QC

- フレーム数と尺が `shotlist.yaml` と一致する。
- 全 PNG がデコードでき、解像度が一致する。
- ffprobe の結果（コーデック、画素形式、色タグ、フレームレート）が 12.1 と一致する。
- 完全な黒フレーム、および同一フレームの連続が、トランジション以外の箇所にない。

全項目の合格後に、キーフレームと記述子と実績コストを台帳へ追記する。

## 14. 実装

### 14.1 CLI コマンド

すべて `fractal-harness <command> <production-id> [options]` の形で、stdout に JSON を1個だけ出力する。人間向けのログは stderr に出す。

| コマンド | 工程 | 内容 |
|---|---|---|
| `describe` | — | 軸の値域、工程とゲート、カットの役割とトランジション、調整用設定 |
| `tuning show` / `tuning write <path>` | — | 調整用設定の表示と、編集用 YAML の書き出し |
| `init` | S0 | 制作ディレクトリ、指定制約、予算の作成。調整用設定をスナップショットする |
| `next` | 全 | 現在の工程、未達条件、実行可能なコマンド |
| `scout run` / `scout select` | S1 | ロケハン。近傍の再探索は `scout run --around <loc>` |
| `brief check` | S2 | スキーマ、指定制約、軸差分。全合格で S3 へ進む |
| `shotlist check` | S3 | カットのコンパイル、スキーマとブリーフとの一致、経路検査、重複禁止 |
| `animatic` | S3 | 全尺の低解像度動画と指標 |
| `look preview` | S4 | ルック確認画像と指標 |
| `proof` | S5 | 有無比較、品質決定、時間見積もり、プルーフ動画、圧縮耐性 |
| `review submit` | S3〜S5 | 批評役の判定を登録。その工程の測定系ゲートが全合格のときだけ受け付ける |
| `kill` | S2〜S5 | 破棄して S1 へ戻る |
| `produce` / `status` | S6 | 本番ジョブの実行と進捗 |
| `encode` | S7 | 動画合成と QC、台帳追記 |
| `ledger import` / `ledger list` | — | 台帳の初期登録と一覧 |
| `measure <scene.yaml>` | — | 既存のシーンファイルを測る人間向けの較正用コマンド。読みやすさ指標、品質決定、予算に対する見積もりを返す。制作では使わない |

### 14.2 レンダラー側に必要な変更

必須:

- デバイスを保ったままシェーダーだけを差し替える API（実装済み: `Renderer::replace_fractal`）。形状ごとにデバイスを開き直すと遅く、WSL の GL バックエンドでは約70個目でアダプターが取得できなくなる。
- フレームごとの GPU 描画時間を返す API（実装済み: `RenderedImage::gpu_time`）。
- `LoadedScene` をファイルを介さずに構築する API（既存の公開フィールドで足りる）。

実測して採否を決める高速化候補:

- PNG 圧縮と書き出しを描画スレッドから分離する。
- 画素ごとの収束判定による適応サンプリング。
- 空や遠景の画素での早期打ち切り。

形状の多様性のための拡張（別トラック）:

- DSL の orbit 命令の追加。現状は8種類で、`formula_family` の値域がこれで決まる。命令の追加は AST、検証、CPU 解釈、WGSL 生成を同時に行う既存の手順に従う。
